# qires.co.uk — maintainer's guide

This is the QI Resolved website. It is a **static site**: there is no database and no
admin login. You change text by editing files in this repository, and the site rebuilds
itself when those changes are pushed.

This guide is for whoever keeps the words and pictures up to date. You do not need to
know HTML for most of it.

---

## 1. The quickest possible version

| I want to change... | Edit this file |
|---|---|
| The nine "What the app does" items | `data/features.yaml` |
| The partner profiles (name, role, one line, LinkedIn) | `data/partners.yaml` |
| The privacy policy | `content/privacy.md` |
| The contact email address, or social media links | `config.toml` |
| The names in the left-hand menu | `config.toml` |
| Everything else on the home page (headline, Our Story, Pricing, Disclaimer) | `layouts/index.html` — see [section 6](#6-editing-the-home-page-text) |

Change a file, save it, commit and push. The live site updates a couple of minutes later.

---

## 2. How the site is put together

The site is built with [Hugo](https://gohugo.io), which takes your text files plus a set
of page templates and produces finished HTML.

```
config.toml       Site-wide settings: title, email, menu, social links, colours
content/          Page text, written in Markdown
data/             Lists of repeated things (features, partners)
layouts/          Page templates — the HTML. Mostly leave alone
static/           Files served exactly as they are: images, fonts, stylesheets
assets/           Source material: the brand artwork, and the stylesheet source
public/           The built site. Never edit — it is regenerated every build
```

The whole website is a **single page** with sections you scroll through, plus one
separate page for the privacy policy.

### Markdown

Files in `content/` are written in Markdown, which is plain text with a few simple marks:

```markdown
## A heading

A normal paragraph. Leave a blank line between paragraphs.

**Bold text** and *italic text*.

- A bullet
- Another bullet

1. A numbered item
2. Another one

[A link](https://example.com) and an [email link](mailto:hello@qires.co.uk).
```

At the top of every file in `content/` there is a block fenced by `---`. That is settings,
not page text. Keep it:

```markdown
---
title: "Privacy Policy"
description: "How QI Resolved handles personal data"
---
```

## 3. Files you can safely edit

**`data/features.yaml`** and **`data/partners.yaml`** — lists. Each entry starts with `-`.
Indentation matters: keep the spaces exactly as they are in the existing entries.

```yaml
- title: Defect hierarchy
  body: >-
    No hardcoded template. Defects are referenced by room, and the hierarchy is
    sorted once the inspection is done.
```

The `>-` means "the text below, joined into one paragraph". Keep it, and keep the
following lines indented further than the `body:` line.

To add a feature, copy an existing block, paste it below, and change the words. To remove
one, delete its whole block including the leading `-`.

**`content/privacy.md`** — ordinary Markdown. Update the date at the top when you change
anything meaningful.

**`config.toml`** — site settings. The parts you are most likely to touch:

```toml
[params]
  tagline = "A new workflow for quinquennial inspections"
  email = "hello@qires.co.uk"
```

and the left-hand menu, where `id` must match a section on the home page:

```toml
  [[params.sections]]
    id = "our-story"
    label = "Our Story"
    image = "img/church-1.jpg"
```

and the social links:

```toml
  [[params.social]]
    name = "Facebook"
    icon = "facebook"
    url = "https://www.facebook.com/..."
```

Only `facebook`, `linkedin` and `instagram` icons exist. Adding another platform needs a
developer to add its icon.

## 4. Files you should NOT edit

| File or folder | Why |
|---|---|
| `public/` | Generated on every build. Your changes will be wiped. |
| `static/css/tailwind.css` | Generated by `make css`. Edits are overwritten. |
| `static/css/fonts.css` | Generated by `make fonts`. Edits are overwritten. |
| `static/fonts/` | The Inter typeface. Leave alone. |
| `layouts/partials/` | Page furniture (header, footer, menu). Ask a developer. |
| `layouts/_default/` | The page shell. Ask a developer. |
| `.github/workflows/`, `.gitlab-ci.yml` | The publishing process. Ask a developer — and note the two must be changed together. |
| `scripts/` | Build tooling. Ask a developer. |

`static/css/custom.css` is hand-written and *is* the right place for style changes — but
it is CSS, so treat it as a developer file.

## 5. Adding images

1. Put the file in **`static/img/`**. Use a plain lowercase name with hyphens and no
   spaces: `st-marys-tower.jpg`, not `St Mary's Tower (1).JPG`.
2. Reference it in a Markdown page with:

   ```
   {{< img src="st-marys-tower.jpg" alt="The tower from the south-west" >}}
   ```

   `alt` describes the picture for people using a screen reader, and shows if the image
   fails to load. It is not optional — please write one.

   To add a caption underneath:

   ```
   {{< img src="st-marys-tower.jpg" alt="The tower from the south-west"
           caption="South-west elevation, 2026" >}}
   ```

**Before you upload:**

- Photographs: save as **JPG**, about **1600px wide**, under **500KB**.
- Drawings, logos, line art: save as **PNG**.
- Resize before uploading. A 6MB photo straight off a camera will make the page slow.

**Changing a left-hand menu illustration:** put the new file in `static/img/`, then point
the `image =` line in `config.toml` at it.

**Check you are allowed to publish it.** Photographs of church interiors may show people;
if anyone is identifiable, you need their agreement before the picture goes on the site.
See section 4.2 of the privacy policy.

## 6. Editing the home page text

Most of the home page wording lives in `layouts/index.html`, mixed in with HTML. This is
the one place where you will see tags. The rule is simple:

**Change the words between the angle brackets. Do not change the angle brackets.**

```html
<h2 class="...">Pricing</h2>
<p>Not yet set. QI Resolved is in development.</p>
 ↑        ↑                                    ↑
 leave    change this bit                      leave
```

Some practical warnings:

- If a line ends with `{{` or starts with `}}`, leave that line alone entirely.
- Never delete a `<` or `>` by accident. If the page looks broken afterwards, undo your
  change rather than trying to patch it.
- Text is written in **British English** — "organisation", "recognised", "programme".
- `&mdash;` and `—` both produce a dash. Either is fine.

If a change feels risky, make it, preview it locally (section 7), and only commit when it
looks right.

## 7. Previewing your changes before they go live

You do not have to publish to see your work.

### The easy way — Docker

If you have [Docker](https://www.docker.com/products/docker-desktop/) installed:

```bash
make serve
```

Then open **http://localhost:1313** in a browser. Leave it running: edit a file, save, and
the browser refreshes on its own. Press `Ctrl+C` in the terminal to stop.

The first run downloads a couple of build tools and takes a few minutes. Later runs are
quick.

### If you have Hugo installed directly

```bash
hugo server
```

Same address, same behaviour.

### Other commands

| Command | What it does |
|---|---|
| `make serve` | Preview locally with live reload |
| `make build` | Build the finished site into `public/` |
| `make css` | Rebuild the stylesheet. **Needed if you add styling to a template** |
| `make fonts` | Re-download the Inter typeface. Rarely needed |
| `make clean` | Delete `public/` and downloaded tools |

## 8. Publishing

Push to the `main` branch. GitHub Actions rebuilds the site and publishes it, usually
within two or three minutes.

```bash
git add .
git commit -m "Update pricing wording"
git push
```

You can watch the build on the repository's **Actions** tab. A green tick means it is
live; a red cross means the build failed and the old site is still up. Opening the failed
run shows what went wrong — most often a typo in a `.yaml` file.

> GitHub Actions is what publishes the site. There is also a `.gitlab-ci.yml` that builds
> the same site on GitLab as a cross-check; it produces an artifact but does not deploy.
> **If a developer changes one, they must change the other.** Both files carry a note at
> the top saying so, and both call the same `scripts/build-css.sh`, so the stylesheet at
> least cannot be built two different ways.

## 9. The look of the site

Colours come from the QI Resolved logo, with the background taken from the original design
mockup:

| Colour | Used for |
|---|---|
| Orange `#F36B22` | The big headline, card outlines |
| Burnt orange `#B24A12` | Smaller orange text, links, menu labels |
| Navy `#22346E` | Body text, the rule through the logo |
| Slate `#3C5553` | Quieter supporting text |
| Cream `#FAF5D8` | The page background |

The burnt orange exists because the logo orange is too pale against the cream for small
text to be readable. **Please do not use the bright orange for body text.**

The typeface is Inter throughout, served from our own site.

To change a colour you must edit it in **two** places, `assets/css/tailwind.css` and
`static/css/custom.css`, then run `make css`. That is a developer job.

## 10. If something goes wrong

**The site looks unstyled — plain black text on white.**
The stylesheet failed to build. Run `make css`, then preview again.

**A change does not appear.**
Check you saved the file, and that the build passed on the Actions tab. If you edited
`public/` by mistake, that is why — see section 4.

**The build failed with a YAML error.**
Almost always indentation in `data/features.yaml` or `data/partners.yaml`. Compare your
entry with the one above it; the spaces must line up exactly. Tabs are not allowed —
use spaces.

**I have broken something and want to start again.**

```bash
git checkout -- path/to/file      # undo changes to one file
git status                        # see what you have changed
```
